# YouTube Focus Mode

A Manifest V3 Chrome extension that turns YouTube into a distraction-free
learning platform: when Focus Mode is on, you only see content from channels
you actually follow. Algorithmic recommendations, Shorts, autoplay, and the
entertainment-oriented sidebar sections disappear.

---

## Install (load unpacked, for development or personal use)

```bash
npm install
npm run build
```

Then in Chrome:

1. Go to `chrome://extensions`.
2. Turn on **Developer mode** (top right).
3. Click **Load unpacked** and select the generated `dist/` folder.
4. Open YouTube — Focus Mode is on by default.

`npm run watch` rebuilds on every file change (click the refresh icon on the
extension card in `chrome://extensions` after each rebuild to pick it up).

├── src/

│   │   ├── constants.ts         Storage keys, message names, CSS hide-class names
│   │   ├── storage.ts           Typed chrome.storage.sync read/write/subscribe

│   │   ├── selectors.ts         *** THE FILE TO EDIT WHEN YOUTUBE CHANGES ITS HTML ***

│   │   ├── rules/                One file per feature, each a pure function of settings -> DOM
│   │   │   ├── homepage-redirect.ts
│   │   │   ├── hide-shorts.ts

│   │
│   └── popup/

### Design decisions, and why

**Redirect the homepage instead of filtering it.**
YouTube's home page is an open-ended stream of shelf types that changes
often. Rather than trying to identify and hide every current and future
shelf, `/` is redirected straight to `/feed/subscriptions` (a strictly
chronological feed of channels you follow). This is the single biggest
reliability decision in the project — it turns an unbounded content-detection
problem into a one-line redirect. `hide-recommendations.ts` still hides the
grid as a defense-in-depth safety net in case the redirect is ever disabled
or races the page load, but the redirect is what actually carries the
feature.

**One shared MutationObserver, not one per rule.**
`observer-manager.ts` owns a single observer on `document.documentElement`
and fans a debounced (150ms) callback out to every rule. This bounds the
performance cost to "one observer, one debounce" regardless of how many
features are enabled, and avoids the redundant DOM walking that one-observer-
per-feature would cause. The observer also ignores mutations that are just
our own class-list toggles, so hiding an element doesn't re-trigger a scan of
itself.

**One CSS class per feature, not one shared "hidden" class.**
`HIDE_CLASSES` in `shared/constants.ts` gives Shorts, recommendations,
navigation, the watch-page sidebar, and comments each their own class. If
they all shared one class, turning off a single feature (removing the class
from "its" elements) risks also un-hiding elements a different, still-active
rule was responsible for. Per-feature classes make each rule's on/off toggle
fully independent of the others.

**Selectors centralized in one file, structural over text matching.**
Every CSS selector and URL pattern lives in `content/selectors.ts`, so a
YouTube markup change is (almost always) a one-file fix. Within that file,
tag names and `href` patterns are preferred over matching visible text —
YouTube ships 100+ UI languages, so a selector that reads the word "Shorts"
only works for English users, while a selector that reads `href="/shorts"`
works everywhere.

**Settings live only in `chrome.storage.sync`.**
The popup never keeps its own state; it reads storage on open and writes a
patch back on every change. The background worker and every content script
read the same storage and subscribe to `chrome.storage.onChanged`. This
means there is exactly one source of truth, and it's what lets `sync`
storage carry your settings across your other signed-in Chrome installs for
free.

## Extension lifecycle

**Chrome starts.** `background/service-worker.ts`'s `onStartup` listener
re-creates the 1-minute schedule-check alarm (MV3 service workers don't
persist `setInterval` state between restarts — alarms are the durable
replacement) and refreshes the toolbar badge from whatever is already in
storage.

**A YouTube tab opens.** The content script, declared with
`run_at: "document_start"`, executes before YouTube's own scripts. It reads
settings from `chrome.storage.sync` (async — see "Known limitations" below),
applies every rule once, and starts the shared observer.

**The user navigates inside YouTube (SPA route change).** YouTube is a
single-page app: clicking a video, a channel, or the logo doesn't reload the
page, it fires a custom `yt-navigate-finish` event on `document`.
`observer-manager.ts` listens for that event and re-runs every rule
immediately (not debounced), so a route change is reflected without waiting
out the mutation debounce window.

**Focus Mode or an individual setting changes (from the popup, the keyboard
shortcut, or the schedule).** Every write goes through `shared/storage.ts`,
which writes to `chrome.storage.sync`. That triggers
`chrome.storage.onChanged` in every open context — the content script's
`onSettingsChanged` listener re-runs `applyAll()` with the new settings, and
the popup (if open) re-renders to match.

**YouTube lazily loads more content (infinite scroll, a new shelf streaming
in).** The shared `MutationObserver` (subtree + childList) picks up the new
nodes, debounces 150ms in case more are still arriving, then re-runs every
rule — newly-inserted Shorts, shelves, or nav entries get hidden the same way
the initial page load's did.

## Edge cases considered

| Case | Handling |
|---|---|
| SPA navigation | `yt-navigate-finish` listener, see above |
| Lazy loading / infinite scroll | MutationObserver with debounce |
| Live streams | Not specifically filtered — a live stream you're subscribed to behaves like any other subscription video; live streams only appear via recommendation/trending surfaces, which are already hidden |
| Playlists | Explicitly kept in the nav allow-list; playlist pages aren't touched by any rule |
| Embedded YouTube videos (on other sites) | Content script only matches `*://*.youtube.com/*`, so embeds on third-party pages are unaffected — intentional, embeds aren't the distraction surface this extension targets |
| Age-restricted videos | Unaffected; no rule inspects age-gating |
| Premium accounts (no ads) | Unaffected; nothing here touches ads |
| Dark / light mode | Popup theme is independent of YouTube's own theme and follows system/light/dark per user choice; hiding rules work identically in either |
| Incognito | Works if the user enables "Allow in Incognito" for the extension (Chrome requires explicit opt-in per extension); `chrome.storage.sync` is unavailable in a fully offline/incognito-only context, in which case settings fall back to `DEFAULT_SETTINGS` for that session |
| Multiple tabs | All read the same `chrome.storage.sync`; a change in one tab's popup applies to every open tab via `onChanged` |
| Extension updates | `onInstalled` only seeds defaults on `reason === "install"`, never on `"update"`, so an update never resets a user's saved settings |
| Offline mode | The content script and its CSS are bundled locally (no CDN/remote code), so hiding rules keep working offline; only the YouTube page itself needs a network connection |
| `music.youtube.com` | Explicitly excluded via `exclude_matches` in the manifest — it's a distinct product and out of scope |

## Known limitations

- **Brief flash before settings load.** `chrome.storage.sync.get` is
  asynchronous, so there's a small window (typically single-digit
  milliseconds) between the content script starting and rules first applying
  where unhidden content could theoretically flash. In practice this is
  faster than YouTube's own render of recommendation shelves, but it's a
  known tradeoff rather than a guarantee.
- **Selector drift.** YouTube changes its DOM without notice. All selectors
  live in `content/selectors.ts` specifically so this is a fast, one-file
  fix — see the comment block at the top of that file for the exact steps to
  diagnose and update a broken selector.
- **English-only text fallback.** A small number of nav-hiding matches fall
  back to matching English label text when no `href` is available. This is
  documented in `selectors.ts`; it only affects the (rare) case where a
  guide entry has no href to test.

## Publishing checklist (Chrome Web Store)

1. `npm run build`, confirm `dist/` loads cleanly via "Load unpacked".
2. Bump `"version"` in `manifest.json`.
3. Zip the **contents** of `dist/` (not the `dist/` folder itself) into a
   single archive.
4. Upload via the Chrome Web Store Developer Dashboard.
5. Since the extension only requests `storage`, `alarms`, and a
   `youtube.com` host permission, the review's permission-justification step
   should be straightforward — the store listing should explain each in one
   sentence (already covered by the "why" comments in `manifest.json`'s
   neighboring source files).
